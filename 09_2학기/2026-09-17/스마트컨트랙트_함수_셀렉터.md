# "function selector was not recognized"와 컨트랙트 배포본 불일치

- **Category:** #Blockchain #Solidity #Ethereum #Hardhat

<br>

## 새롭게 알게 된 것

- 컨트랙트 함수를 호출하는 트랜잭션의 data 앞 4바이트는 **함수 셀렉터**다. 함수 시그니처 문자열(예: `transfer(address,uint256)`)을 keccak256으로 해시한 값의 앞 4바이트다.
- 그래서 함수 이름이 같아도 **인자 타입이 바뀌면 셀렉터가 달라진다.** 예를 들어 가격 인자를 `uint256` 하나에서 구역별 가격 배열 `uint256[5]`로 바꾸면 완전히 다른 함수가 된다.
- 체인에 배포된 바이트코드에 그 셀렉터가 없으면 EVM은 fallback으로 가고, fallback이 없으면 `function selector was not recognized`로 revert한다.
- 즉 이 오류는 대부분 **백엔드가 쓰는 ABI와 체인에 배포된 컨트랙트 버전이 다르다**는 뜻이다. 연결 문제가 아니다.
- Hardhat 같은 인메모리 개발 체인은 재시작하면 상태가 사라지고, 같은 배포 키·같은 순서로 다시 배포하면 컨트랙트 주소도 똑같이 나온다. CREATE로 만든 주소는 배포자 주소와 nonce만으로 정해지기 때문이다. 그래서 주소는 맞는데 코드는 옛날 버전인 상황이 생길 수 있다.

<br>

## 예제 코드

```bash
# 1) 연결부터 확인: 체인 ID가 돌아오면 RPC 연결은 정상이다
curl -s -X POST <RPC_URL> \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","method":"eth_chainId","params":[],"id":1}'

# 2) 백엔드가 부르는 함수의 셀렉터 계산 (Foundry cast, 시그니처는 예시)
cast sig "registerShow(uint256[5],string)"

# 3) 배포된 바이트코드 안에 그 셀렉터가 있는지 확인
cast code <CONTRACT_ADDRESS> --rpc-url <RPC_URL> | grep -i <셀렉터 앞 8자리>
```

```javascript
// ethers.js로 셀렉터 직접 계산
import { id } from "ethers";
const selector = id("transfer(address,uint256)").slice(0, 10); // "0xa9059cbb"
```

## 겪었던 문제 / 트러블슈팅

- **문제 상황**: 공연을 등록하는 트랜잭션이 전부 `function selector was not recognized`로 실패했다. 백엔드 시더는 "체인 접근(방화벽·키)을 확인하라"는 경고를 찍어서, 처음엔 연결 문제로 보였다.
- **원인**: 그날 아침 컨트랙트 코드에서 등록 함수의 가격 인자가 구역별 배열로 바뀌었는데, 원격 체인 컨테이너는 전날 배포본 그대로였다. 백엔드가 보내는 새 셀렉터가 배포된 바이트코드에 없었다.
- **해결 방안**: `eth_chainId`로 연결이 정상인 걸 먼저 확인해서 연결 문제를 지웠고, 셀렉터가 배포본에 없는 걸 확인했다. 체인 컨테이너를 최신 컨트랙트로 다시 배포하자 등록 트랜잭션이 바로 성공했다. 컨트랙트를 고치면 배포까지 한 번에 하도록 순서를 맞추는 게 중요하다는 걸 배웠다.
